## 1. 项目概述

- **任务类型**：二分类预测（O2O 优惠券核销预测）
- **预测目标**：`P(核销 | 用户, 商户, 优惠券, 领券时间)`
- **业务价值**：把"无差别群发优惠券"变为"给高意向用户发券"，提升核销率、降低投放成本
- **技术栈**：Python · Pandas / NumPy · scikit-learn（决策树） · XGBoost · Matplotlib
- **关键成果**：定位并修复了导致 AUC 虚高（0.98）的三类数据泄漏，重建为时间切分的无泄漏评估（真实 AUC ≈ 0.63）

## 3. 业务背景与问题定义

O2O 平台为刺激消费发放大量优惠券，但大部分券被领取后闲置，**核销率极低、投放成本浪费**。本项目的目标是：对每张已领取的优惠券，预测该用户**领券后 15 天内是否到店核销**，从而指导"给谁发、发什么券"。

### 正负样本定义

```
gap = (date - date_received).days        # 核销间隔天数（未核销为 NaN）
class = 1  if  gap <= 15                 # 领券后 15 天内到店核销（有效转化）
class = 0  其他                          # 未核销 或 15 天后才核销
样本 = 仅 coupon_id 非空的行              # 未领券记录不构成样本
```

**为什么是 15 天**：优惠券有效核销窗口约两周。数据实测显示第 15 天仍有 896 笔核销、第 16 天 824 笔，**核销量在 15 天边界平滑过渡、无断层**——说明 15 天来自业务规则而非人为硬切。

数据来自天池 O2O 优惠券赛题（2016 年 O2O 优惠券使用预测）。

| `discount_rate` | 折扣率（`0.8` 或 `150:20` 满减） | 特征 |
| `distance` | 用户到商户距离 | 特征 |
| `date_received` | 领券日期 | 时间 / 标签来源 |
| `date` | 到店消费日期（空 = 未核销） | 标签来源 |

## 5. 数据探索（EDA）

完整分析见 [`docs/探索性分析.html`](docs/探索性分析.html)。

### 5.1 描述性统计要点

- 数据量 164.9 万行，`distance` 均值 2.36、75% 分位 3、最大 10（距离分布右偏，多数用户距离商户很近）
- `date_received` 覆盖 2016-01-01 ~ 2016-06-15，`date` 覆盖至 2016-06-30

### 5.2 缺失结构（核心发现：缺失由业务结构导致，而非数据质量）

| 字段 | 缺失数 | 缺失率 | 业务含义 |
|---|---|---|---|
| `coupon_id` | 701,602 | 42.55% | **未领券**记录（用户直接到店消费） |
| `date` | 880,114 | 53.38% | **未核销**记录（领券后未使用） |

- 有效消费记录 768,767；有效领券记录 947,279；领券后消费记录 67,165

### 5.3 记录类型分布（标签映射的依据）

| 记录类型 | coupon_id | date | class | 数量 | 占比 |
|---|---|---|---|---|---|
| 未领券（仅消费） | 空 | 有值 | —（不进样本） | 701,602 | 42.6% |
| 领券未核销 | 有 | 空 | 0 | 880,114 | 53.4% |
| 领券·15 天内核销 | 有 | 有 | **1** | 57,060 | 3.5% |
| 领券·15 天后核销 | 有 | 有 | 0 | 10,105 | 0.6% |

**建模样本 = 领券记录合计 947,279 行**。

### 5.4 关键洞察

1. **严重类别不平衡**：正样本仅约 6%，Accuracy 无意义，需用 AUC 等排序指标，并用类别权重处理。
2. **缺失即业务**：coupon_id / date 的高缺失分别对应"未领券"与"未核销"两类业务行为，不是脏数据，不能简单删除或填充。
3. **未领券记录不进样本、但提供用户/商户的历史行为**，可用于特征统计。

## 7. 特征工程

### 7.1 总体思想：多粒度聚合

原始数据是**事件粒度**（一行 = 一次领券事件）。预测核销与否，单看这一行信息太薄，**核销主要由"主体是谁"决定**。因此特征工程的核心是把事件行展开为三份主体画像：

```
事件行 = 用户画像 + 商户画像 + 券画像 + 事件属性(距离/折扣/时间)
            │           │          │
        按user_id   按merchant_id  按coupon_id
        分组聚合      分组聚合       分组聚合
```

每个特征都对应一条**业务假设**：

| 粒度 | 特征 | 业务假设 |
|---|---|---|
| 用户 | `user_use_coupon_rate` ★ | 用户越爱用券 → 越可能核销（归一化剔活跃度，纯券敏感度） |
| 用户 | `user_use_coupon_times` / `user_consume_times` | 用券 / 消费活跃度 |
| 用户 | `user_receive_unused` | 领了不用 → 大概率再浪费 |
| 用户 | `user_mean_interval` | 历史核销越快 → 冲动/刚需（⚠ v1 泄漏元凶） |
| 商户 | `merchant_launch_coupon_used_rate` | 商户券转化率高 → 更可信 |
| 商户 | `merchant_launch_coupon_count` / `merchant_mean_interval` | 发券活跃度 / 券核销速度 |
| 券 | `coupon_used_rate` | 券本身受欢迎度（v1 计算有 bug，v2 修复） |
| 券 | `coupon_fifteen_used_count` | 券历史正样本数 |
| 事件 | `distance` / `discount_rate` | 便利度 / 折扣吸引力 |

### 7.2 特征构建三原则

1. **多粒度聚合**：把事件行展开成用户 + 商户 + 券画像
2. **归一化优先**：次数 → 比率，剔除活跃度混淆，得到纯净的"券敏感度"
3. **ID 抽象成画像**：才能泛化到没见过的用户/券（直接 one-hot ID 做不到）

### 7.3 关于泄漏的关键认知

特征工程中 `coupon_fifteen_used_count` 等券特征**本质是"标签在券粒度的聚合"**（它的计算条件 `gap <= 15` 与标签完全相同）。这正是 v1 泄漏的根源（见第 10 节）。

## 8. 模型构建

| 模型 | 参数/策略 |
|---|---|
| **决策树** | GridSearchCV（max_depth∈{5,8,10,15}，min_samples_split∈{50,100,200}，min_samples_leaf∈{20,50,100}），`class_weight='balanced'`，3 折 CV 以 AUC 选优 |
| **XGBoost** | GridSearchCV（max_depth∈{4,6,8}，learning_rate∈{0.05,0.1}，n_estimators∈{100,200}），`scale_pos_weight = 负样本/正样本 ≈ 15.9` |

**类别不平衡处理**：`scale_pos_weight` / `class_weight='balanced'` 本质是提高少数类误分的惩罚权重，等效于过采样。

**为什么用 AUC 评估**：不平衡场景下 Accuracy 无意义（全猜负也有 94%）；AUC = 随机正样本排在随机负样本之前的概率，只看**排序**，与"投放 = 给用户排序取头部"的业务天然对齐。

## 10. 关键复盘：数据泄漏诊断与修复

**这是本项目最有价值的部分：一个"高指标先怀疑泄漏"的完整实践。**

### 10.1 现象

v1 报告 AUC 0.984 / 0.987。**高得反常**——正样本率仅 6% 的任务不可能达到 0.98，领域常识约 0.7 左右。第一反应不是庆祝，而是排查泄漏。

### 10.2 定位到三类泄漏

| 类型 | 机制 | v1 中的表现 |
|---|---|---|
| **① 目标泄漏** | 特征 = 标签生成量 | 标签由 `gap = date - date_received` 定义；特征 `user_mean_use_coupon_interval` 正是该量的用户级均值 → 与标签相关 **-0.56**，特征重要性 **0.79~0.92** |
| **② 自指泄漏** | 聚合含自身行 + 未来 | 聚合按**全量数据** groupby，当前行自己的核销结果计入自己的特征（正样本被自身抬高）；1 月记录的特征里混入该用户 2-6 月的未来消费 |
| **③ 重叠泄漏** | 随机切分跨集共享 | `train_test_split` 随机切分，同一 user/merchant/coupon 同时进训练与验证，验证集"记住"了训练画像 |

### 10.3 验证方法（对照实验）

| 实验 | AUC | 结论 |
|---|---|---|
| 全特征 + 随机切分（v1 原样） | 0.984 | 精确复现 v1 |
| 只删 `user_mean_use_coupon_interval` | 0.980 | **几乎不掉** → 泄漏是机制性的、冗余分布 |
| 删全部用户/券泄漏聚合特征 | 0.886 | 仍偏高 → 剩余特征仍含自身行 |
| **时间切分 + 聚合只算训练段（v2）** | **0.586 / 0.627** | 真实水平 |

> 关键认识：**单独删特征治不了本**——泄漏冗余分布在多个聚合特征里，模型删一个、从另一个补回来。必须改聚合的**数据范围**（只用训练段）并改**切分方式**（时间切分），才能截断泄漏。

### 10.4 修复方案（v2）

1. **时间切分**：1-5 月训练 / 6 月验证 / 7 月测试
2. **无泄漏聚合**：用户/商户/券聚合特征**只在训练段计算**，验证/测试特征值全部来自训练历史（不含自身行、不含未来）
3. **修复退化特征** `coupon_used_rate`（v1 分子分母统计同一批记录，比率恒等于 1）
4. **恢复 `discount_rate`**（v1 错误排除）

### 10.5 教训

> 任何高指标，**先怀疑泄漏，再庆祝**。判断方法：检查特征是否可由标签条件重算出来、聚合是否混入验证/测试段数据、切分是否尊重时间顺序。

## 12. 结论与展望

- **结论**：完成了一个从探索到评估的完整 O2O 券核销预测项目，并通过对数据泄漏的系统诊断，把虚高的 AUC 修正到可信区间——模型的"真实水平"远低于初版报告，但**评估过程的可信度**大幅提升。
- **展望**：
  - **逐行历史聚合**：当前聚合按"训练段整体"统计，训练段内部仍含自身行；可改为按"该行领券时刻之前"逐行滚动聚合，做到训练集内也严格无泄漏
  - **更多特征**：用户活跃度、券与用户历史偏好匹配度、商圈距离聚类等
  - **模型**：LightGBM / CatBoost、交叉验证 + 早停，配合 top-k 领取率等业务指标评估
